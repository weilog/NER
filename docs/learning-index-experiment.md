# 从真实实验学会 NER、对照设计与代码

阅读顺序：本文件 → reports/index-factorial-findings.md → reports/index-factorial-results.md → 对应代码。
这里所有实测来自你的分支；我们围绕一个问题把数据、程序、评分和结论连起来，而不是逐个背名词。

## 1. 为什么做这轮实验

词典记住名称，HMM 统计字符与标签概率，CRF 根据上下文特征学习标签序列；LLM 通过提示完成抽取。
它们最终都要交回原文中的实体、类别和位置。LLM 即使输出了正确的名称，也可能没有数对字符位置。
历史首版试跑 20 条中 5 句出现坐标问题，7 个实体符合“end 少加一”的特征；第二版没有，但同时改了索引和说明。
因此，旧试跑提出了假设，却不能告诉我们两个改动分别是否有效。

本轮不是再堆一个模型，而是把错误机制拆开，用两因素对照验证。这就是个人贡献从功能实现走向研究证据的过程。

## 2. 将想法变成可控制的变量

独立变量是你主动改变的因素；因变量是你观察的结果；控制变量是在组间保持一致的条件。

| 角色 | 本轮内容 |
|---|---|
| 因素一 | 两列普通索引 / 三列边界索引 |
| 因素二 | 基本半开区间定义 / 额外终点解释与长度检查 |
| 观察结果 | 坐标错误率、Token/实体 P/R/F1、文字类别诊断、费用和延迟 |
| 固定条件 | 模型、Thinking、温度、4 条 Train 示例、类别定义、200 条 Dev、评分器 |

四组是 A=普通+简短，B=三列+简短，C=普通+明确，D=三列+明确。
这样 B-A 对应表示因素，C-A 对应解释因素。比较 D-C 与 B-A 是否相同，可以检查两因素的交互作用。
交互作用不代表一定存在“协同增益”，也可能是重复解决同一问题或没有可辨变化。

## 3. 为什么另取固定 Dev，而不是重复那 20 条

反复根据同一批样本修改提示，就逐渐适应了这些样本。旧试跑适合找问题，不适合证明修改能推广。
`experiments/index_factorial.py` 的 `select_ids()` 排除原试跑与既定调参子集，再按 seed 和 ID 的 SHA256 排序取 200 条。
排序不看 gold，不根据成绩换种子。清单在 data/splits/index_factorial_v1.json。
它仍然是 Dev；传统模型此前在完整 Dev 上选参，且研究者已看过 main 的结果，所以不冒充新的独立 Test。

你可以检查：200 个 ID 是否唯一，是否与排除列表相交，四组是否完全相同。测试会自动验证这些条件。

## 4. 读懂生成请求的代码

打开 `src/ner_experiment/llm/index_prompts.py`。
`indexed_text()` 只做原文到结构化输入的转换：

```python
# 两列
[[i, char] for i, char in enumerate(text)]
# 三列
[[i, char, i + 1] for i, char in enumerate(text)]
```

三列提前给出每个字符之后的位置。以“张三”为例，字符索引为 0、1，完整实体跨度为 [0,2)，而不是 [0,1)。
这不是修改答案，而是改变同一段原文的位置展示方式。非 BMP 字符也按 Python Unicode 码点编号。

`system_prompt()` 根据解释因素决定是否加入“end=末字符索引+1”和长度检查说明；它不按索引组改变类别定义。
`build_request()` 为每组放入相同示例 ID、顺序和 assistant 标准输出，只按本组形式展示 user 输入。
目标输入的关键调用是：

```python
build_request(row['text'], examples, arm, config)
```

传入的是目标原文，不是目标 entities。目标 gold 只在调用结束后的评分阶段使用，这防止了答案泄漏。
4-shot 指上下文里有四条示例，没有更新模型参数；它与 CRF 使用 9,538 条样本训练不同。

## 5. 请求、解析、规范化是三个步骤

`llm/client.py` 负责实际请求、有限重试、持久缓存及账本；`llm/prompts.py` 的 `parse_response()` 检查返回 JSON 外壳。
JSON 合法不等于实体正确。一个实体仍可能类别未知、坐标越界、缺少文字或与原文切片不一致。
`evaluation/metrics.py` 的 `normalize_prediction()` 做统一校验、去重和重叠处理，然后用同一非重叠实体集合计算两级主指标。
本轮不自动把错误 end 加一，不按 gold 搜索位置，不发额外模型修复请求。
无效条目虽然不进入主集合，但无效数、原始跨度分数与失败率都单独披露，不能只展示清洗后的漂亮数字。

## 6. 为什么保存原始响应和缓存

同一个模型即使 temperature=0，也不保证重新调用得到完全相同的输出。
缓存键包含样本 ID、完整请求、endpoint、提示版本与解析器版本；新增版本参数保持旧缓存键不变，同时隔离四组实验。
SQLite 先持久化原始响应，再解析；程序中断时可以恢复已收到的响应。
JSON 键顺序可能在缓存重建后改变，因此新实验在首次导出时就固定对象键顺序，不改变列表次序或任何预测值。
这使字节哈希变化真正反映内容变化，避免把纯编码差异误认为预测改变。

## 7. 并发与预算为什么要一起设计

最多四个请求同时进行，每条句子的四组请求按固定哈希顺序交错发送，减少整组先后时段的混杂。
每个线程有自己的连接；账本用 SQLite 的事务在发送前预留费用，因此四个线程不能同时把同一份余额当成可用。
响应到达后按真实 usage 结算，释放多余预留。未知扣费保留预留，不偷偷重置账本。
请求本阶段 12 元、全项目 100 元，达到上限前停止；这两者约束不同范围。

`sum_peak_reservations_without_settlements_cny` 是所有请求都按上限预留且从不结算的总和，不是预计真实费用。
本轮 800 次实际请求全部成功，新增费用估算 0.607699 元，全项目累计 0.637521 元；费用估算不等于供应商账单。

## 8. 怎样把输出变成分数

TP 是正确预测，FP 是错误预测，FN 是遗漏。

```text
Precision = TP / (TP+FP)
Recall    = TP / (TP+FN)
F1        = 2TP / (2TP+FP+FN)
```

Token 正确要求一个字符的完整 BIO 标签相同。把 I-name 预测为 B-name 也算错，会贡献 FP+FN。
O→O 不贡献主要 TP；否则大量背景字符会抬高成绩。
严格实体正确要求同一句话中 start、end、type 完全一致。部分边界正确可以保留一些 Token TP，却没有完整实体 TP。
micro 先汇总全体 TP/FP/FN，再计算；macro 是先各类计算，再平均。本轮另存十类实体结果。

本轮结果：

| 组 | 坐标错误句子 | Token F1 | 实体 F1 |
|---|---:|---:|---:|
| A | 6/200 | 77.19% | 73.66% |
| B | 1/200 | 78.75% | 74.23% |
| C | 5/200 | 78.32% | 73.59% |
| D | 1/200 | 79.00% | 73.52% |

三列组的坐标错误较少，但更详细的说明没有带来额外实体 F1 优势。最高 Token F1 的 D 并非最高实体 F1 的 B。
因此，学习实验时不要只找“最强的一行”，应检查改动究竟解决了哪个问题、还留下什么问题。

## 9. 文字识别和坐标一致性怎样分开看

`evaluation/index_diagnostics.py` 计算忽略坐标的文字+类别多重集指标，并记录坐标错误和闭区间终点特征。
多重集保留重复提及的次数；同一输出副本去重，但仍不能判断模型指的是哪一次同名出现。
`occurrences()` 只搜索原文中模型自己给出的文字，不使用 gold。唯一出现表示它可被唯一定位，不保证类别正确。

真实 dev:1189 中，“建筑设计师”位于 [21,26)。A 写出了正确文字，却给 end=25；B/C/D 的同一实体输出 [21,26)。
这是模型输出内部坐标不一致的直接证据。
真实 dev:689 中，B 虽修正了短地址本身的位置，仍将原标注要求的整个长地址拆开。坐标自洽不等于符合标准实体边界。
完整对照见 reports/index-factorial-findings.md。

bag F1 不是主指标上界：主评分过滤无效条目，而 bag 保留部分带文字的无效输出，二者集合不同。不要将差值直接解释成定位损失比例。

## 10. 区间为什么需要配对、重新汇总计数

打开 `experiments/index_analysis.py` 的 `paired_contrasts()`。
每次随机抽句子 ID，同一个抽样结果用于所有组，然后汇总每组 TP/FP/FN 并重新计算 micro F1。
如果先计算每句话 F1 再平均，就会让实体很少与很多的句子等权，回答的是不同问题。

本轮 B-A 的实体 F1 差为 +0.57 个百分点，2000 次重采样的描述性 95% 区间为 [-1.50,+2.70]。
区间同时容纳下降和上升，意味着这批证据不足以宣布稳定改善；不能说差值为正就“证明有效”。
它也不意味着方法完全无用。应结合坐标错误从 6 句到 1 句的观察，以及输入 token 约增加 27% 的成本作出有限结论。
多个比较未做多重校正，且没有重新调用多次模型，所以这些区间不覆盖全部随机性，也不是正式确证检验。

## 11. 你怎样亲手复现和读代码

在项目根目录，用已有环境依次运行：

```powershell
# 读旧试跑并重算，不发请求
.\.venv\Scripts\python.exe scripts\audit_pilot_positions.py
# 逐条验证全部新缓存，保护原始记录和账本，不发请求
.\.venv\Scripts\python.exe scripts\verify_index_factorial.py
# 离线重算配对区间和报告，不发请求
.\.venv\Scripts\python.exe scripts\analyze_index_factorial.py
```

`run_index_factorial.py --dry-run` 只检查计划；省略参数在缓存缺失时会真实付费调用，请先理解账本与计划。
已有上下文和源码不一致时会拒绝覆盖，这是保护结果的设计。需要新假设时建立新的实验版本，不改旧结果。

建议阅读顺序：configs/index_factorial_v1.json → llm/index_prompts.py → experiments/index_factorial.py → evaluation/index_diagnostics.py → experiments/index_analysis.py。
先看测试中的最小例子，再看真实记录，能把每个函数的输入、输出和失败条件对应起来。

## 12. 这轮哪些是你的研究工作

你可以通过亲手核验案例、理解并检查因素隔离、审阅标注疑点、复现统计与解释取舍，形成真实的个人贡献。
AI 辅助实现与自动运行应如实声明，不能把自动诊断当作两人已经独立完成的人审。
本轮的贡献是可追溯的错误机制对照与边界分析，不是“换了一个更强模型”或“证明通用最优提示”。
后续先完成对结果的人工理解与审核，再决定是否将某个候选用于正式 Test；不要因 Dev 的一行最高分立即覆盖冻结方案。
